## 3. 分工结论：谁留在 ESP32-S3，谁搬到 RK3568

### 留在 ESP32-S3（实时性 / GPIO 时序，Linux 用户态做不好）
- **HX711 称重** —— 用户态 bit-bang 会被调度打断
- **I2S 语音**：录音 + TTS + 唤醒词
- **WS2812 灯 + 物理按键** —— 单线时序 + 中断
- **DHT22 温湿度** —— 单总线时序
- **RFID**（UART）—— 留这边也顺手
- **HC_SR04 超声波** —— 建议直接废弃（RK 有雷达，功能更强）

### 搬到 RK3568（算力 / 存储 / 网络密集）
- **视觉识别** —— NPU + 摄像头，YOLO 远强于 Edge Impulse 三分类。**这是最核心的搬移**
- **视觉 + 重量融合** —— 融合算法是纯计算，但输入来自 RK 的视觉，放 RK
- **商品 / 库存 / 订单 / 购物车 / 收银 / 会员** —— SQLite 对 RAM+SPIFFS，掉电不丢
- **WebServer / 网页 / 顾客端 PWA / 管理后台** —— 236 KB 的 `WebServer.cpp` 是 ESP32 的负担
- **报表 / 数据分析 / 大屏 / 商家 AI 分析**
- **OCR**
- **雷达**（RK 独有）
- **扫码枪** —— RK 上已实现且更稳（8095，带 TTL 缓存，290ms → 3ms）

### 保持独立，不动
- **`re_min` 热敏打印机** —— 它是打印头控制器，不是主控。
  打印链路**保持原样**：浏览器渲染中文 → 384-dot 单色光栅 → 打印机轮询
- **`MimiClaw`** —— 独立 AI 助理角色，与主控并列

## 6. 今晚踩过的坑（省你明天重复踩）

| 坑 | 现象 | 处理 |
|---|---|---|
| **板端 curl 走代理** | 访问 `127.0.0.1` 被环境代理绕出去超时 | **必须加 `--noproxy '*'`** |
| **本机 curl 假报失败** | `-o /dev/null` 返回 `dl=0 speed=0` | 判断下载必须 `-o 真实文件` |
| **scoop python 建的 venv 没 pip** | `No module named pip` | 建完先 `python -m ensurepip --upgrade` |
| **Git Bash 路径被吃掉** | `/f/xxx` 传给原生 exe 变成 `F:\f\xxx` | 若设了 `MSYS_NO_PATHCONV=1`，**先用 `cygpath -m` 转** |
| **Bash 里多行 `python -c`** | 换行被吞，报 `command not found` | 复杂脚本写成 `.py` 文件再跑，别用 `-c` |
| **改文件只差一个空白** | 手滑把换行删了，文件 SyntaxError | 替换时 `old_string` 要带足够上下文 |
| **类名差一个字符** | `grape` vs `grapes`，概率恒为 0 且**不报错** | 跑 `05_check_labels.py` |

> **`grape` vs `grapes` 这个坑最阴**：融合引擎按名字取概率
> （`probabilities.get(rule.label, 0.0)`），名字对不上就拿到 0，
> **不报错、不告警**，表现只是「这个水果怎么都识别不了」。
> 改类别 / 改模型 / 改规则表之后都要跑一遍 `05_check_labels.py`。
