## 4. 新增服务：收银后端（8094）

### 4.1 为什么这样设计

v1 的 ESP32-S3 把整个商品表放在 RAM 里，每次变更都把完整 JSON 重写进 SPIFFS。
掉电、看门狗复位都可能丢数据，而且退款要重新解析 `"可乐x2, 薯片x1"` 这种展示字符串
来恢复库存——商品名里只要含 `x` 就会静默算错。

本版改用 SQLite 作为唯一数据源：

- 退款直接读 `order_items` 记录恢复库存，不再解析展示字符串。
- 结算在**同一个事务**里扣库存 + 写订单行，不会出现"扣了库存没建订单"。
- 金额每步都过 `round_money()`，避免浮点漂移出现 `0.30000000000000004` 这种小票。
- 跨天归零用墙钟日期比较（Linux 时钟可信），不再依赖 NTP 回调。

### 4.2 数据表

```text
products(code PK, name, price, stock, today_sold, mfg_date, shelf_life,
         category, is_weigh, updated_at)
orders(id PK, created_at, total, paid, method, status, session_id, paid_at)
order_items(id PK, order_id, code, name, price, qty, is_weigh, source)
cart_items(id PK, session_id, code, name, price, qty, is_weigh, source, added_at)
daily_stats(day PK, revenue, items_sold)
scan_events(id PK, code, source, matched, name, created_at, consumed)
sku_map(label PK, code, min_conf)      -- 留给未来的 SKU 模型
op_logs(id PK, ts, user, action, detail)
settings(k PK, v)
```

初始商品沿用 v1 的 8 条真实数据（条码、名称、价格、库存、生产日期、保质期均一致），
所以原有商品二维码继续可用。

数据库路径：`/home/linaro/ai/store/store.db`（WAL 模式）。
小票目录：`/home/linaro/ai/store/receipts/`。

### 4.4 小票打印

ESC/POS 字节流，中文按 **GBK** 编码（58mm 热敏打印机无 UTF-8 模式）。

- 未配置打印机时：只生成文件 `/home/linaro/ai/store/receipts/order-<id>-<时间>.escpos`。
- 配置后：写入 `/dev/usb/lp0` 之类的设备节点。
- 当前板端**没有** `/dev/usb/lp0`（未接打印机），所以走文件路径。

> 注意：金额符号必须用全角 `￥`(U+FFE5)。半角 `¥`(U+00A5) **不在 GBK 码表内**，
> 会变成 `?`，这个坑本轮已经踩过并修掉。

### 4.5 视觉集成边界（重要）

`/api/vision/observe` 只在 `sku_map` 里有映射时才会加购。当前视觉模型是通用 COCO
YOLO11n，`sku_map` 为空，所以调用它**只会记录未匹配**，不会凭空猜 SKU。
这符合 v1 第 11 节"不要把 COCO 结果当成 SKU 识别完成"的要求。

## 5. 新增服务：扫码枪（8095）

v1 第 10.6 节要求条码作为 SKU 主确认源。服务支持两种传输：

| 模式 | 说明 |
|---|---|
| `evdev` | 扫码枪出厂默认的 USB HID 键盘模式。直接解析 `/dev/input/eventN` 的 `struct input_event`，**不依赖 python-evdev**（Debian 10 没有该包）。 |
| `serial` | 扫码枪设为"USB 虚拟串口"模式时的 CDC 设备。**会自动跳过 `/dev/lidar`**，绝不抢雷达的 `/dev/ttyACM0`。 |

未插枪不是错误：服务保持 `waiting_device` 并每 2 秒重扫，板子可以不带枪启动。

识别策略：**只认设备名里带扫码枪关键词的设备**（barcode/scanner/zebra/honeywell/
newland/datalogic 等），明确排除 keyboard/mouse/touchscreen/keypad。宁可不认，也不
误抓触摸屏——触摸屏被抢走比不识别更糟。

API：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 状态网页 |
| GET | `/api/scanner/status` | 状态、传输方式、设备、统计 |
| GET | `/api/scanner/events?limit=` | 最近扫码记录 |
| GET | `/api/scanner/devices` | 当前所有输入设备与串口候选 |
| POST | `/api/scanner/inject` | `{code, add_to_cart?}` **无硬件时测试用** |
| POST | `/api/scanner/config` | `{mode, device, baud}` 热切换配置 |

无硬件时的验证方式：

```bash
curl -s --noproxy '*' -X POST -H 'Content-Type: application/json' \
  -d '{"code":"6901234567890"}' http://127.0.0.1:8095/api/scanner/inject
# → {"ok":true,"message":"识别为 可口可乐 330ml", ...}
```

配置为串口模式（例如枪设为虚拟串口）：

```bash
curl -s --noproxy '*' -X POST -H 'Content-Type: application/json' \
  -d '{"mode":"serial","device":"/dev/ttyACM1","baud":9600}' \
  http://127.0.0.1:8095/api/scanner/config
```

> 若枪在 HID 模式下不工作，先在枪的说明书里找"USB 键盘 / HID"条码扫一下，
> 或改用 `serial` 模式。

## 6. 新增服务：OCR 辅助（8096）

**本机未安装 `tesseract`**，且热点环境下没有可达的软件源，所以识别接口目前会
明确返回"引擎未安装"，不会伪造结果。

已完成并**通过测试**的是真正决定成败的部分：标签解析与目录匹配。

- 容量提取：`330ml` / `550毫升` / `250 mL` / `75g` / `1.5L` / `500克` 等写法。
- 包装噪声剥离：`净含量`/`配料`/`生产日期`/`保质期` 等**只去标签、不丢整行**，
  因为真实包装上"可口可乐 净含量 330ml"常在同一行。
- 目录匹配：对商品名做最长公共子串打分，低于阈值返回"无把握匹配"，
  避免把 OCR 噪声变成自信的错误 SKU。

API：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 状态与解析测试网页 |
| GET | `/api/ocr/status` | 引擎状态、语言包、统计 |
| POST | `/api/ocr/parse` | `{text}` **无需引擎**，直接验证解析与匹配 |
| POST | `/api/ocr/recognize` | `{use_raw:true}` 或 `{image_path}` 执行识别 |

装上引擎后即可启用识别：

```bash
sudo apt-get install -y tesseract-ocr tesseract-ocr-chi-sim
```

解析逻辑自测：

```bash
python3 /home/linaro/ai/ocr/ocr_service.py --parse "可口可乐 净含量 330ml"
```

## 7. 模型安全替换工具（`/home/linaro/ai/deploy_model.sh`）

对应 v1 第 10.5 节。强制"先备份、再离线验证、最后才动线上模型"的顺序，
验证不过就拒绝安装，坏模型不可能把线上检测链路打挂。

```bash
sudo ./deploy_model.sh /path/to/new_model.rknn   # 校验→离线验证→备份→安装→重启→检查
sudo ./deploy_model.sh --verify-only new.rknn    # 只验证，不安装
sudo ./deploy_model.sh --list                    # 看当前模型与备份
sudo ./deploy_model.sh --rollback                # 回滚到最近备份
```

流程细节：

1. 校验 RKNN magic（`RKNN\x00\x00\x00\x00`），快速给出清晰报错，而不是运行时的
   `Invalid RKNN format`。
2. 用 `yolo11_infer.py` 对单张真实图片跑离线推理，检查 JSON 里 `detections` 有效。
3. 备份现有模型到 `/home/linaro/ai/models/backups/`（带时间戳）。
4. 安装 + 重启 `rk3568-vision.service` + 轮询 `8088` API。
5. API 起不来则自动回滚。

> **关键坑**：RKNN 运行时（`rknnlite`）装在 **linaro 的用户级 site-packages**
> （`~/.local/lib/python3.7/site-packages/rknnlite`），**不是系统级**。所以脚本内部
> 一律用 `sudo -u linaro -H python3` 跑推理；直接用 root 跑会
> `ModuleNotFoundError: No module named 'rknnlite'`。这个坑本轮已踩并修掉。

## 11. 本轮踩到并修掉的坑（供后续参考）

| 现象 | 根因 | 处理 |
|---|---|---|
| `/tmp` 里的待部署文件消失 | `/tmp` 会被清理 | 部署文件放到工程目录，不要长期依赖 `/tmp` |
| 小票金额显示 `?7.00` | 半角 `¥`(U+00A5) 不在 GBK 码表 | 改用全角 `￥`(U+FFE5) |
| 小票生成报 `'is_weigh'` KeyError | `order_items` 查询漏选该列 | 补齐字段 |
| `deploy_model.sh` 报无 `rknnlite` | 运行时装在 linaro 用户级 site-packages，root 看不到 | 用 `sudo -u linaro -H python3` |
| 扫码枪状态接口 290ms | 每次状态查询都对 8 个 event 设备做 ioctl | 加 2 秒 TTL 缓存 → 3.4ms |
| 本机测试连不上 127.0.0.1 | shell 里继承了 `http_proxy` | 测试脚本显式 `ProxyHandler({})` |
| 扫码枪 Shift+字母解不出字符 | 字母只在基础键码表，shift 只改大小写 | 回退查基础表后再转换大小写 |

### 14.3 已发现并规避的关键坑：原始 ONNX 不能用

随权重发布的 `my_model-simplified.onnx` 是 **OAK / Luxonis 导出，只有 3 个输出**
（`output1..3_yolov6r2`，每尺度一个融合张量）。

板端 `yolo11_infer.py` 的后处理按 **9 输出**布局写死（`pair = len(outputs) // 3`，
每尺度 `box_dfl / class_scores / score_sum`），喂 3 输出模型会 `IndexError`。

**规避方式**：必须从 `.pt` 用 ultralytics 重新导出标准单输出 ONNX，由 RKNN 自己切成 9 输出，
板端代码零改动。转换脚本内置该检测：若发现 3 输出 ONNX 且带了 `--no-export`，直接报错退出。

### 14.4 已完成的验证（板端实测）

用现有 COCO `yolo11n_i8.rknn` 在 8099 端口**干跑**水果服务，验证除权重外整条链路：

```text

inference_ms : 121.25        pipeline_ms : 213.12        loop_fps : 4.69
detections   : 4 条，含 confidence 与 box
infer_errors : 0             fetch_errors : 0
```

结论：**取帧 → letterbox → 9 输出 DFL 解码 → NMS → JSON 契约**全部打通，
`.rknn` 一到位只需换模型文件，无需再动代码。类别名超出给定列表时会回退成 `class_N`，
属预期防御行为。干跑实例已清理，8099 已关闭，8088/8089 未受影响。
