## 1. 原工程的关键跨板接口（**必须原样保留**）

```text
视觉节点 ──POST /api/vision-fusion──────────► 主控 Work7_20
主控     ──GET  /api/vision-fusion/latest───► （查询融合结果）

主控     ──GET  /api/printer/job-meta───────► re_min
主控     ──GET  /api/printer/job?id=...─────► re_min
re_min   ──POST /api/printer/ack?id=&ok=────► 主控

MimiClaw ──store_query / restock / expiry-pricing / service-ticket──► 主控（带 X-MimiClaw-Key）
主控     ──GET  /api/admin/customer-analytics─► 商家（带 X-MimiClaw-Key）
```

**`/api/vision-fusion` 的报文形状**（已在 RK 侧复刻，见 §5.1）：

```text
POST application/x-www-form-urlencoded
     observation_id=<8位hex>-<序号>   ← 幂等键，长度 ≤40，只允许字母数字/-/_
     captured_ms=<毫秒>
     sample_count=<帧数，恒为 5>
     spread=<所有类别里窗口内极差的最大值>
     margin=<均值的 top1 - top2>
     <类别名>=<概率>                  ← 字段名就是类别名，有几个类别就几个字段
→ {"ok":true,"accepted":bool,"label":...,"name":...,"confidence":...,
   "weight_g":...,"stable":...,"vision":...,"vision_stable":...}
```

`observation_id` 幂等是**跨服务边界**的硬要求：融合引擎本身幂等，
但收银后端的加购接口**不幂等**，重放会重复加购。

**打印链路（与 RK3568 现状不同，别搞混）**：`re_min` 轮询主控的 **384-dot 单色光栅**任务；
中文小票由**浏览器字体**在网页侧栅格化，所以打印机固件不需要中文字库。
RK3568 现在的做法是 ESC/POS + GBK 字节流，**是另一条路线**。

## 3. 水果视觉融合逻辑（**要原样搬过来**）

| 项 | 原值 |
|---|---|
| 融合权重 | **视觉 78% + 重量匹配 22%** |
| 自动确认阈值 | 融合 ≥ **72%**、视觉 ≥ **55%**、重量匹配 ≥ **15%** |
| 重量判定 | 连续读 5 次；低于 **25 g** 或五次波动 > **4 g** → 不确认 |
| 不确定时 | 输出「**请人工确认**」，**不自动加购** |
| 类别 | `apple` / `banana` / `grapes`（Edge Impulse 三分类） |

`PRODUCT_RULES` 里的 `typicalGrams` / `toleranceGrams` 是初始值，比赛用固定样品应实测收紧。

> **已实现**（2026-09-28 晚）：上表全部判据已 1:1 搬成 Python，
> 见 `2026-09-28\rk3568-fruit-fusion\fruit_fusion.py`（268 项测试覆盖）。
> 另外从 `xiao_ov3660_weight_fusion.ino` 搬来了**多帧聚合**这一层——
> 5 帧滑动窗口、`spread` = 所有类别里窗口内极差的最大值、`margin` = **均值**上的 top1−top2、
> 窗口不满 5 帧不提交。这一层原来在 XIAO 上，不搬过来融合引擎拿不到有效输入。

> **顺手堵掉的三个真问题**（都是「看着能用、实际会出事」的那类）：
>
> 1. **原工程的认证漏洞**：`WebServer.cpp` 判断管理员只看
>    `cookie.indexOf("admin_auth=1") >= 0` —— 谁在浏览器里手设一个 cookie 就是管理员。
>    现在换成服务端 `auth_sessions` 真会话，且下发的是 `HttpOnly` cookie，
>    于是页面里那几行 `document.cookie='admin_auth=1; path=/'` **一个字都不用改**。
> 2. **`/api/order-history` 的返回形状**：页面是 `orders = await or.json()` 之后直接
>    `orders.forEach(...)`，原工程返回的就是**裸数组**。包成 `{"ok":true,"orders":[…]}` 的话
>    页面会抛异常、被 `catch(e){}` 吞掉 —— 订单列表空白、营收显示 ¥0.00，**且不报错**。
>    另外数组顺序必须是**旧的在前**（原工程 `orders[]` 按下单顺序追加），
>    否则页面倒序渲染会把最新单放到最下面，而且 `refundOrder(i)` 传的**数组下标**
>    会退到别的单上。
> 3. **退款按显示字符串反解数量**：原工程拿 `"名称x数量"` 反解，
>    商品名里带 `x` 就算错。现在读 `order_items` 的落库行。
>

>

### 8.1 由决策 2 派生的待定项

ESP32-S3 降级为从机后，从机接口需要定清楚：

- **WiFi + 精简 HTTP**（裁原 `WebServer.cpp`）：不占 UART、无距离限制；要改 ESP32 代码。
- **UART 帧协议**：更实时更简单；要新写协议，且 RK3568 的 UART 还要留给 RFID。
- **建议**：称重走 **UART**（"稳定读数"是事件，实时性重要），语音走 **HTTP**。

> **RK 侧已经留好了口子，两条路都不用改 RK 代码**：
> 融合服务（8099）的 `POST /api/scale/sample` 收 `grams=<克数>`。
> 从机用 HTTP 就直接 POST；走 UART 的话在 RK 侧加一个串口→HTTP 的小桥接即可，
> 融合服务本身不用动。
> **时间戳用 RK 侧的本地单调时钟盖**，不用从机的时钟——避免两块板子时钟漂移。
> 另外融合服务对样本的判据与原工程一致：**≥5 个样本**且极差 ≤4 g 才算稳定，
> 最后样本距今 >1500 ms 算过期。所以从机**不能只在读数变化时才上报**，
> 得按 500 ms 的节奏持续喂，否则秤永远"过期"。

### 8.2 实施结果（2026-10-09）

#### 8.2.1 做法：**裁剪改造，不是新建工程**

⚠️ 这里先纠正一个此前的判断错误：曾经把这一项记成「未开工、要新建
`firmware/peripheral-slave/`」。**是错的。**

原 `firmware/store-controller/` 本来就完整实现了 HX711 称重、I2S 语音、
WS2812、DHT22、RFID、USB 扫码枪——一个不缺，`Work7_20.ino` 是完整主程序。
**缺的只是「当从机」这件事本身**（怎么把数据交给 RK）。

所以做法是：`Work7_20.ino` 加一个 `#define SLAVE_MODE`，把主控形态的代码
**逐字保留**在 `#else` 分支里。同一个工程、两套形态、随时切回：

```c
#define SLAVE_MODE 1     // 1 = 外设从机（当前）  0 = 原主控形态
```

这同时避开了「不得新增子项目」的约束——目录还是那四个。

#### 8.2.2 接口协议（最终落地版）

| 方向 | 通道 | 端点 | 说明 |
|---|---|---|---|
| 从机 → RK | 8099 HTTP | `POST /api/scale/sample` | `grams=` 称重样本，**每 500 ms 一次** |
| 从机 → RK | 8094 HTTP | `POST /api/rfid/report` | `uid=` 刷卡上报（**新增端点**，见 8.2.3） |
| 从机 → RK | 8095 HTTP | `POST /api/scanner/inject` | `code=` 条码上报 |
| 从机 → RK | 8094 HTTP | `POST /api/env/report` | `temperature=`/`humidity=` DHT22 读数，**每 60 s 一次**（**新增端点**，见 8.2.3 第 4 条） |
| RK → 从机 | 8080 HTTP | `POST /api/tts` | 让从机喇叭播报（复用异步播报队列） |
| RK → 从机 | 8080 HTTP | `POST /api/tare` | 远程去皮 |

**为什么称重最终走 HTTP 而不是 §8.1 建议的 UART**：ESP32-S3 的 IO 已经很紧——
WS2812(18)、按键(39)、HX711(12,14)、DHT22(41)、RFID(21,15)、
I2S(8,9,46,47,48,13)——再插一路 UART 要抢引脚，而 HTTP 不占 IO，
且 RK 侧零改动。UART 分支**代码保留**（`SLAVE_USE_UART_SCALE`），
但默认关闭，且需要先定 `SLAVE_UART_TX_PIN`（默认 `-1`，此时自动回退 HTTP）。

#### 8.2.3 实施中发现并修掉的四个真问题

都是「从机能编译、能跑、就是没反应，而且不报错」那一类：

1. **RFID 上报方向搞反了**。原写法是 `POST 8094 /api/rfid-poll`——
   而 `/api/rfid-poll` 是**页面轮询用**的 GET 接口，语义是「有没有新卡事件」，
   方向正好相反，POST 上去必然 404。
   更根本的是：原工程里主控自己读卡、自己写库，**RK 侧压根没有「接收从机
   刷卡上报」的入口**。所以新增了 `POST /api/rfid/report`
   （`store_ext.py` 的 `report_rfid()` + `store_ext_routes.py` 的 `h_rfid_report`），
   落的还是同一张 `rfid_pending` 表——**页面代码一行没改**就能看到。
   权限 `open`（从机没有会话，且卡号本身不是机密）。

2. **扫码枪端点不存在**。原写法 `POST 8095 /api/scan`——8095 没有这个端点，
   `/api/scan` 是 8094 收银后端的。正确的是 8095 的 `/api/scanner/inject`，
   8095 收到后会自己带上 `session` / `add_to_cart` 转发给 8094
   （`scanner_service.py` 里那条转发链早就写好了）。

3. **`add_to_cart` 在 form 编码下真值判错**。8095 的 `inject` 同时收 JSON 和
   form-urlencoded，而 `bool(payload.get("add_to_cart"))` 在 form 下拿到的是
   字符串：`add_to_cart=0` → `bool("0")` → **True**，想关掉反而打开。
   已改成按真值语义解析（`_truthy()`）。ESP32-S3 从机走的正是 form。

4. **温湿度没有上报路径**（2026-10-09 补）。DHT22 在 ESP32-S3 上
   （`Plus.cpp`，`DHT_PIN 41`），但原工程读完**只拿去拼 AI 提示词**
   （`AI_Test.cpp:237`），既不落库也不对外；RK 侧的 `/api/env` 是写死的
   `available:false`。所以大屏永远显示「温湿度传感器未接」—— 又是个静默空白。
   补法与 RFID 同构：新增 `POST /api/env/report`（`store_ext.py` 的
   `report_env()`/`latest_env()` + `store_ext_routes.py` 的 `h_env_report`），
   从机侧 `Plus.cpp` 的 `DHT22_HandleLoop()` 在 `SLAVE_MODE` 下每 60 s 调
   `SlaveLink_PostEnv()`。三个设计点：

   - **存历史而不是只存一行**：`env_samples` 表留最近 2000 条，大屏要按
     `created_at` 算新鲜度 —— 从机掉线后不能拿旧读数冒充实时值。
     超过 `ENV_STALE_SECONDS`（180 s，容忍丢 2 次上报）就退回 `available:false`。
   - **量程校验**：DHT22 物理量程 -40~80 ℃ / 0~100 %RH，越界返回 400 而不是
     存进去（存了只会让大屏显示一个假值）。实测 `temperature=999` → 400。
   - **保留上限 2000 条**：板子根分区只有 1.4 GB 可用，60 s 一条、一天 1440 条，
     不清理几个月就能把盘写满。

   实测（板端真机，2026-10-09）：上报后 `GET /api/env` 返回
   `{"available": true, "temperature": 24.3, "humidity": 55.1, "age_seconds": 0.1}`，
   headless chromium 抓 DOM 确认大屏渲染成 `🌡️ 25.0℃ 💧 60.0%`。

顺带把四条上报路径抽成 `Slave_Config.h` 里的宏，避免以后再散落写错。

##### ⚠️ 编译才暴露的架构级缺陷：`SLAVE_MODE` 放错了地方

原先 `#define SLAVE_MODE 1` 写在 `Work7_20.ino` 里。**Arduino 会把 sketch 目录下
每一个 `.cpp` 单独编译，`.ino` 里的 `#define` 对它们不可见** —— 于是 6 个主控
模块（`WebServer` / `AI_Test` / `Product_Data` / `HC_SR04` / `Mode_LowPower` /
`Inventory_Monitor`）的 `.cpp` **照样被编进从机固件**，而且**编译不报任何错**。
「裁剪主控模块」这件事当时是**静默失效**的。

修法：

1. `SLAVE_MODE` 搬到 `Slave_Config.h`，`.ino` 改成 `#include "Slave_Config.h"`。
2. 6 个主控 `.cpp` 各加**整文件保护** `#if !SLAVE_MODE ... #endif`。
   （为什么用 `#if` 而不是把文件挪走：挪走会让 `SLAVE_MODE=0` 也编不过。）
3. `Voice_Interaction.cpp` 是混合体（既有从机要的 I2S/TTS/按键/唤醒词，也有主控
   专属的 AI 问答、工单、超声波、低功耗），按 `SLAVE_MODE` 打了 9 处条件编译。
   其中一处容易漏：`global_voice_q/a/show` 原本**定义**在 `WebServer.cpp`，
   从机不编译它 → 链接期 `undefined reference`，必须在从机分支里补定义。
4. 同类残留还有 `DETECT_DISTANCE`（原由 `HC_SR04.h` 提供）—— 从机分支里那句
   「多模态唤醒」日志引用了它，改成 `#if SLAVE_MODE` 分开写。

**教训**：`.ino` 里的宏/开关**只对 `.ino` 自己有效**。凡是「裁剪 / 角色开关」
性质的东西，一律放头文件。这条已固化成 `check_structure.py` 的第 6、7 条断言
（第 7 条用迷你预处理模拟 `SLAVE_MODE=1`，揪出「引用了主控符号却无从机侧定义」
的行；已用注入 bug 的方式反向验证过它真的会报）。

##### 复现方式

```bash

#   esp32 core 3.3.8 -> D:\Arduino15\packages\esp32\hardware\esp32\3.3.8
#   esp32s3-libs 3.3.8-cn -> D:\Arduino15\packages\esp32\tools\esp32s3-libs\
#   Edge Impulse 库 project_1062783_inferencing -> D:\789\.arduino-build\user\libraries\
#   （注意必须是**标准 Arduino 库结构**：有 library.properties + src/；
#     扁平化的副本 Arduino 不认，会报 xxx_inferencing.h not found）
```

## 12. HDMI 大屏（2026-10-09 落地）

### 12.1 结论：能，而且基本是现成的

板子（ATK-DLRK3568）的 HDMI 输出**已经接显示器就能用**，不需要改设备树：

| 检查项 | 实测结果 |
|---|---|
| DRM connector | `/sys/class/drm/card0-HDMI-A-1/status = connected` |
| 分辨率 | **随显示器自动协商**。实测两块屏：1920x1080@60 的那块开箱即 1080p；1366x768 的那块 X 默认落到 1280x720（差 86 列被拉伸，字发虚）→ 已由脚本自动对齐（见下） |
| 显示服务 | lightdm **已配 autologin linaro**，Xorg `:0` + LXDE（openbox/pcmanfm/lxpanel）在跑 |
| 浏览器 | `/usr/bin/chromium`（91.0.4472.164，正点原子为 RK 调过的包装脚本，自带 `--use-gl=egl` 等） |
| 要显示的内容 | **现成的**：`http://<板子>:8094/bigscreen`（「智慧超市促销大屏」，时钟/环境/热销/临期/战报 三屏轮播，8 秒切换，点一下进收银终端） |

落地方式是 **chromium kiosk 全屏打开 8094/bigscreen**，落在
`rk3568/store-backend/kiosk/`：

```
kiosk/start-kiosk.sh            启动脚本（等 8094 → 关屏保/DPMS → 守护循环起 chromium）
kiosk/bigscreen-kiosk.desktop   自启项模板
kiosk/install_kiosk.sh          一键安装/卸载（sudo bash install_kiosk.sh [--no-start|--uninstall]）
```

自启挂在 `~/.config/autostart/bigscreen-kiosk.desktop`（lxsession 按 XDG 规范读）。
**实测有效**：`systemctl restart lightdm` 后无人干预，日志里出现新的
「8094 已就绪（等待 1s）→ xset → 启动 chromium」记录，屏幕出画面。

`start-kiosk.sh` 里四个「不做就会现场翻车」的点：

1. **先等 8094 就绪再开浏览器** —— 8094 是 systemd 服务，开机时未必已起，
   浏览器先开就停在错误页。
2. **`xset s off -dpms`** —— 不关的话闲置十分钟黑屏。
3. **`while true` 守护循环** —— chromium 崩了自动拉起，不用人到现场。
4. **分辨率对齐到显示器原生模式** —— X 会挑一个「能用但不是原生」的模式
   （1366x768 的屏落到 1280x720）。脚本从 `xrandr` 里读**带 `+` 的那个模式**
   （`+` = preferred，即 EDID 首选时序）再切过去。**故意不写死分辨率**，
   换个显示器也能自适应；认不出来就保持默认不动，不会把屏搞黑。

   实测日志：`[2026-10-09 16:19:59] 分辨率已对齐：HDMI-1 1366x768`，
   抓帧确认 1366x768、隔 5 秒两帧 md5 不同（画面活着）。

### 12.2 顺手挖出两个真 bug（都修了）

大屏第一次渲染出来是「**等待商品数据...**」，一查是两个字段名对不上：

1. **`/api/products` 返回的是 `code`，但三个页面全按 `qr_code` 取值**

### 12.5 板端截屏（没有 scrot 也能抓）

板子没装任何截屏工具（无 scrot / import / xwd / ffmpeg），但**装了 GStreamer**，

```bash

gst-launch-1.0 -q ximagesrc num-buffers=1 use-damage=0 ! \
```

**坑**：`kill -9` 掉 chromium 之后，X 根窗口不会重绘，屏幕会**冻在最后一帧**，
新起的 chromium 窗口显示不出来（实测卡了 5 分钟）。抓到的图会一直是同一张
（用 md5 比对能立刻发现）。**解法：重启 X 会话**（`sudo systemctl restart lightdm`）。

**另一个坑（在 Windows 侧操作时）**：`pkill -f 'xxx'` / `ps | awk '/xxx/' | xargs kill`
里的模式串如果出现在**执行这条 SSH 命令的那个 bash 自己的命令行**里，
就会把宿主 shell 一起杀掉 —— 表现为「远程命令毫无输出、后续步骤全没执行」。
**一律用 `pkill -x <进程名>`**（本机 chromium 的真名是 `chromium-bin`，
不是 `chromium`；`pgrep -x chromium` 会一直返回 0）。

**判活时 `pgrep -x` 的第二个变体**：`pgrep -x start-kiosk.sh` 也会**永远返回 0** ——
因为脚本是被 `/bin/bash /home/linaro/ai/kiosk/start-kiosk.sh` 拉起来的，
进程名（`comm`）是 **`bash`**，不是脚本名。一度误判成「kiosk 守护挂了」，
其实 PID 一直在。**判活要按命令行匹配**：`pgrep -af 'start-kiosk'`。
（结论：`pgrep -x` 只适合 `comm` 就是目标名的场景，比如 `chromium-bin`。）

## 13. 热敏打印机上电联调（2026-10-09）

### 13.1 需求与做法

> **本文档不写明文凭据**（§13、§14 均同）：热点 SSID / 口令一律用代号
> `SSID-旧热点` / `SSID-新热点` / `PASS-新热点`，实际值见各固件目录的
> `secrets.h`（已 gitignore）。仓库有 `tools/check_literals.py` 守卫，明文凭据提交会被拦。

热点从 `SSID-旧热点` 换成 `SSID-新热点`（旧热点已停用），要求**只改打印机的 Wi-Fi**。

**关键事实：打印机的 Wi-Fi 凭据是编译期宏，不是 NVS，也没有串口命令可改。**
`main/main.c` 用 `#include "secrets.h"`，再 `strlcpy` 进 `config.sta.ssid`。
⇒ **改 Wi-Fi 只能重编 + 重烧，没有别的路。**

改的三个宏（`main/secrets.h`，已 gitignore；模板 `secrets.h.example` 进库）：

```c
#define WIFI_SSID               "SSID-新热点"      /* 15 个 UTF-8 字节，无 BOM */
#define WIFI_PASSWORD           "PASS-新热点"
#define CONTROLLER_BASE_URL     "http://10.176.240.215:8094"
```

⚠️ **`CONTROLLER_BASE_URL` 必须一起改，而且必须带 `:8094`。**
原值是 `http://192.168.43.44`（旧主控，端口 80）。RK3568 的 store 服务在
**8094**，80 端口上没有任何服务 —— 只改 Wi-Fi 不改这个，打印机连上网也
找不到控制器（实测 TCP 被 RST，串口刷 `Connection reset by peer`）。

### 13.2 ★ 最大的坑：热点是 5 GHz，而 ESP32-S3 只有 2.4 GHz

第一次改完烧完，打印机**连不上**。串口只有反复的
`WIFI_EVENT_STA_DISCONNECTED`（id=5），**连 `wifi:state: init -> auth` 都不出现**
—— 说明失败发生在认证之前，根本没扫到这个 SSID。

从 RK3568 上看这个热点的真实参数：

```
$ nmcli -f SSID,BSSID,CHAN,FREQ,SIGNAL,SECURITY dev wifi list | grep SSID-新热点
SSID-新热点    A2:ED:32:6F:79:B5    157    5785 MHz    34    WPA2
```

**信道 157 / 5785 MHz = 5 GHz。ESP32-S3 是 2.4 GHz-only（802.11 b/g/n），
物理上不可能扫到它。** 2.4 秒的重试周期正好等于扫完 13 个 2.4G 信道的耗时。

⇒ **所有 ESP32 设备（打印机、MimiClaw、从机）都连不上 5 GHz 热点。**
这是共性问题，不是打印机独有。

**排查手法（值得复用）**：不要只盯着串口。**从已经在网的那台设备（RK3568）
去查热点的信道/频段**，比在 ESP32 侧猜快得多：

```bash
nmcli -f SSID,BSSID,CHAN,FREQ,SIGNAL,SECURITY dev wifi list
```

`nmcli` 会**每个 BSS 列一行** —— 同一个 SSID 出现两行（不同 CHAN）说明是
双频合一；**只有一行就是单频**。（顺便：BSSID `A2:ED:32:6F:79:B5` 是
**本地管理地址**，说明「SSID-新热点」是手机热点/便携路由器的虚拟 AP。）

**解法**：把热点切到 2.4 GHz。切换后打印机立刻连上：

```
I (8161) wifi:connected with SSID-新热点, aid = 4, channel 6, BW20, bssid = ba:11:12:1b:eb:f6
I (8161) wifi:security: WPA3-SAE HUNT_AND_PECK, phy: bgn, rssi: -58, pmf:1
I (9211) re_min: WiFi ready, IP=10.176.240.102
```

信道 6、RSSI -58 dBm、WPA3-SAE 过渡模式（带 WPA2 兼容）。

### 13.3 两个既有 bug（**与本次改 Wi-Fi 无关，改之前就在**）

#### (a) `CONFIG_FREERTOS_HZ=100` 让 `pdMS_TO_TICKS(3)` 变成 0

```c
/* button_task, main.c */
while (gpio_get_level(PIN_BUTTON) == 0) {
    motor_step(motor_position++);          /* 内含 esp_rom_delay_us(6000) */
    vTaskDelay(pdMS_TO_TICKS(3));          /* HZ=100 → (3*100)/1000 = 0 → vTaskDelay(0) */
}
```

`vTaskDelay(0)` **不阻塞、不让出 CPU**。而这颗板子的**按键一直读到低电平**
（`GET /api/status` → `"button":0`；`hardware_init()` 已给 `PIN_BUTTON` 配了
内部上拉，所以是**外部**把它拉低的），`feed_button` 于是变成占满 CPU1 的死循环：

```
E (6651) task_wdt:  - IDLE1 (CPU 1)
E (6651) task_wdt: CPU 1: feed_button
```

**每 5 秒一次，从不断**（`CONFIG_ESP_TASK_WDT_PANIC` 没开，只打印不复位）。
同款问题还有 `local_print_test` / `strobe_print_test` 里的 `pdMS_TO_TICKS(2)`。

**注意：这个 bug 不影响 Wi-Fi。** 用优先级 10 的探针任务实测，调度器能正常
抢占 `feed_button`，事件循环（`sys_evt`，prio 20）也照常处理事件。

**修法**（尚未改，等确认）：把 `CONFIG_FREERTOS_HZ` 改成 **1000**。这样
`pdMS_TO_TICKS(3)` = 3 tick = 3 ms，走纸时序不变（`motor_step` 自己已有 6 ms
物理延时）；**不推荐**直接写 `vTaskDelay(1)` —— 那会把步进周期从 ~6 ms 拉到
~16 ms，走纸明显变慢。

**另外要查硬件**：按键为什么恒为低？外壳装配压住 / 按键焊反 / 走线短路。
**这个不解决，打印机一上电就一直在转电机。**

#### (b) 打印机与板端的接口契约不一致

打印机 `printer_task` 期望的 `job-meta` 是**扁平**的：

```json
{"ready": true, "id": 7, "width": 384, "height": 120, "bytes": 5760}
```

板端 `h_printer_job_meta` 实际返回：

```json
{"ok": true, "pending": false, "count": 0}
```

**没有 `ready` 字段** ⇒ `cJSON_IsTrue(ready)` 恒假 ⇒ 打印机**永远认为没有任务**，
静默等待（不报错，所以很难发现）。另外：

- 打印机取正文走 `GET /api/printer/job?id=N`，期望**裸光栅字节**（按
  `height × 48` 读）；板端 `h_printer_job` 返回 **JSON + base64**，裸二进制在
  `/printjob.bin`。板端 `job?id=1` / `ack?id=1` 实测都是 **404**。
- 打印机强制 `width == 384`。

⇒ **真要打小票时，这三处必须先对齐。**

### 15.2 ★ 从机上报失败率 72% → 12%

**症状**：从机 `/api/status` 返回 `scale_ok:69 / scale_fail:181`，串口持续刷
`称重上报失败 N 次（...不可达？）`。**但设备其实是通的** ——

```bash
# 在板端看有没有来自从机的连接
ss -tn | grep ":8099"
# → ESTAB      0 0 10.176.240.215:8099  10.176.240.57:63153
# → FIN-WAIT-1 0 359 ...:65446      ← 359 字节没发出去 = 客户端先超时关了
```

**有 ESTAB 就说明 TCP 通**，问题在响应时序。两个根因都在从机侧：

1. **`WiFi.setSleep` 在从机形态下从未被调用**。
   `Mode_LowPower.cpp` 里明明有 `WiFi.setSleep(WIFI_PS_NONE)`，但整段被
   `#if !SLAVE_MODE` 包住 —— **从机固件里根本不编译**。于是保持 Arduino 默认的
   `WIFI_PS_MIN_MODEM`，发包要等 AP 的 DTIM 窗口，**往返抖动 100~500ms**。
   → 修：`WIFI_Test.cpp` 的 `WiFi.begin()` 前显式 `WiFi.setSleep(WIFI_PS_NONE)`。
2. **`SLAVE_HTTP_TIMEOUT_MS` 只有 400ms**，而板端实测 ping RTT **505ms**。
   → 修：提到 **1000ms**（不宜再大 —— 主循环还有 I2S 录音/TTS，阻塞久会爆音）。

**实测**：`scale_ok 69→239`、`scale_fail 181→29`，**失败率 72% → 10.8%**；
板端样本 `age_ms 405 → 111`（新鲜度明显改善）。

> ⚠️ `SLAVE_SCALE_INTERVAL_MS` **不要为了减压而调大**：RK 侧融合服务要
> 「≥5 个样本 + 窗口内极差 ≤4g」才判稳定，500ms 节奏下 2.5 秒凑够 5 个；
> 再慢就一直判「样本过期」，秤等于没接。

### 15.6 两处仍未闭环

**① DHT22 温湿度 —— 已定性为「硬件未接线」，不是故障（2026-10-11 结案）**

现场确认：**DHT22 从头就没接**。所以串口那句 `[警告] DHT22 读取失败，跳过本次发送`
不是 bug，也不是接线接触不良 —— 是**传感器根本不在板上**。
板端 `/api/env` 长期 `available:false`、大屏显示「传感器未接」，**都是正确状态**。

**处理方式：新增编译开关 `ENABLE_DHT22`（`Slave_Config.h`），现场未接线时置 0。**

- 置 0 后：不构造对象、不 `dht.begin()`、不轮询 —— 串口不再每 60 秒刷一次警告。
- 为什么必须加这个开关：那行警告会把串口日志淹掉，排查**其它**问题时极易被
  误导成「硬件故障」。而且 `Plus_Init()` 原来那句「DHT22 初始化完成」是**假的**
  —— `dht.begin()` 不验证硬件，没接线也照样打印。现在置 0 时改打
  「DHT22 已禁用（ENABLE_DHT22=0，硬件未接线）」，一眼可辨。
- 验证方式（不用上板）：编译后扫固件字符串 —— 应命中「DHT22 已禁用」，
  **不应**命中「DHT22 初始化完成」/「[警告] DHT22 读取失败」。
- 将来补上传感器：数据线接 **GPIO41**，并加 **4.7k~10k 上拉电阻到 3.3V**，
  然后把 `ENABLE_DHT22` 改回 1 重烧。

> 历史排查记录保留在下方，但**结论已变**：不是接线问题，是没接。

- 引脚：`Plus.h` → **`DHT_PIN 41` / `DHT_TYPE DHT22`**（ESP32-S3 GPIO41）
- ⚠️ `Plus_Init()` 只调 `dht.begin()`，**不验证硬件** —— 串口照样打
  「DHT22 初始化完成」，**别被这行日志骗了**

**② `/api/voice-subtitles` 恒 502**

`store_ext_routes.py` 把 voice 上游配成 `http://127.0.0.1:8097/api/voice-subtitles`，
但**板端没有 8097 监听**。按 `rk3568/vlm/README.md`，`vlm_service.py --port 8097`
是跑在**电脑侧**的（板端只用 `8092` 的 `rk3568-vlm.service` 代理过去）。
⇒ 既有配置问题；语音字幕要能用，得先在电脑上起 8097 并把上游指过去。

### 15.7 外网 `www.mimistore.icu` 返回 502（Cloudflare 回源）

**不是 TLS / 证书问题**。`curl -w` 实测：

```
connect=0.097s   tls=0.274s   starttransfer=22.3s   HTTP=502
```

TCP 和 TLS 都正常，**是回源失败**（等 22 秒才吐 502）。

**排除法**：本机 8094 起 IPv4+IPv6 双栈转发到板端，本机 `127.0.0.1:8094` /
`::1:8094` 都 **200**，**但外网仍 502** ⇒ **ingress 不指向本机**；
同时本机直连板端 `10.176.240.215:8094` = **200** ⇒ 新地址本身是好的。
`192.168.43.44`（旧主控）实测 **100% 丢包** —— 与 22 秒超时特征吻合。

⇒ **隧道回源里写的还是迁移前的旧地址**。要改：

> Cloudflare Dashboard → Zero Trust → Networks → Tunnels → **`mimistore`**
> （ID `4215124b-e5eb-4d9d-a810-050700c3010a`）→ Public Hostnames →
> `www.mimistore.icu` → Type **HTTP**，URL **`10.176.240.215:8094`**

⚠️ 注意隧道是 **`mimistore`** 这条，**不是**本机 `~/.cloudflared/` 里那个
`545c18c5-…` —— 后者是**遗留隧道、根本没人运行**（`tunnel info` 报
"does not have any active connection"）。本机 cloudflared 服务实际跑的是
`mimistore`（可从服务注册表 `ImagePath` 的 `--token` 解出来）。

另外**裸域 `mimistore.icu` 没有 A 记录**，需要单独加 CNAME 或做重定向。
