# ATK-DLRK3568 智慧超市项目交接文档

更新时间：2026-09-12

## 1. 项目目标与当前阶段

本项目把原 ESP32-S3 `Work7_20` 智慧超市的“高算力主控”迁移到正点原子 **ATK-DLRK3568**：

```text
USB摄像头 → YOLO11n INT8 / RKNN → 视觉结果
USB二维激光雷达 → 串口协议解析 → 点云/人员区域变化
视觉 + 雷达 → 顾客会话融合状态机
后续：条码、OCR、HX711、RFID、购物车、库存、订单、打印
```

目前已经完成的是“视觉、雷达、融合、商品数据采集”的底座。当前视觉模型是 **COCO 通用 YOLO11n**，只用于验证端到端 NPU 链路；它**不是最终超市 SKU 模型**，不能识别“某品牌某规格饮料”这类具体商品。

## 5. 视觉模块：已做的实现与实测结果

### 模型与运行时

```text
模型：/home/linaro/ai/models/yolo11n_i8.rknn
格式：RKNN INT8，target_platform=rk3568
Runtime：RKNN Toolkit / Lite 2.3.2
NPU Driver：0.8.2
```

模型转换在 VMware Ubuntu 中进行，模型本体已上传到板端。旧系统自带的 `mobilenet_ssd.rknn` 与当前 Runtime 不匹配，曾报 `Invalid RKNN format`，不要再把它当作验证模型。

### 时延优化结果

视觉服务采用“相机采集线程持续覆盖旧帧、推理线程只处理最新帧”的方式，不会发生帧队列越积越旧的问题；网页使用 MJPEG 长连接，而不是逐张轮询图片。

已实测：

| 阶段 | 优化前/基准 | 当前典型值 |
|---|---:|---:|
| NPU 推理 | 约 72–103 ms | 约 70–90 ms |
| Python YOLO 后处理 | 约 54–60 ms | 约 7–13 ms |
| JPEG 编码 | 约 6 ms | 约 6–10 ms |
| 端到端 pipeline | 约 149 ms | 约 87–106 ms |
| 实时循环 | 约 6.3 FPS | 约 9–10.5 FPS |
| 估算显示帧年龄 | 约 150 ms | 约 90–130 ms |

后处理优化利用 YOLO11 的 score-sum 输出先筛掉背景网格，再仅对候选框进行 DFL 和类别解析。基准中旧后处理为 `54.31 ms`，新实现为 `2.08 ms`，且同一帧检测结果完全一致。

### 视觉源文件

```text
/home/linaro/ai/yolo11/vision_service.py
/home/linaro/ai/yolo11/yolo11_infer.py
/home/linaro/ai/models/yolo11n_i8.rknn
```

最近一次升级已加入 `/raw.jpg`。这一路原始帧不带识别框，专门给数据采集服务使用，避免为了采集训练数据再打开第二个 `/dev/video9` 消费者。

### NPU 注意事项

一次视觉服务重启前，日志中出现过：

```text
RKNN: failed to submit
```

通过受控恢复解决：停止服务、`SIGKILL` 清除卡死的旧推理进程，再重启服务。恢复后实测恢复到约 `92 ms / 10.2 FPS`。

若再次发生“8088 在监听、但 API 不返回”的情况，执行：

```bash
sudo timeout 5 systemctl stop rk3568-vision.service || true
sudo systemctl kill -s SIGKILL rk3568-vision.service 2>/dev/null || true
sleep 2
sudo systemctl reset-failed rk3568-vision.service
sudo systemctl start rk3568-vision.service
```

然后等 10–15 秒预热并检查：

```bash
curl --noproxy '*' http://127.0.0.1:8088/api/vision/result
```

## 6. 雷达模块：真实协议、已修正的问题与验证

### 硬件与协议

上位机截图对应 FAI/S2-YJ 类二维旋转激光雷达；板子识别为 STC USB CDC 串口设备。上位机的设定为 `S2-YJ / 150000 baud`。

采到的真实完整包示例：

```text
AA 55 00 08 3D 67 6B 6A 1D 51
11 70 33 12 38 33 12 1C 33 13 F8 32
13 D0 32 14 A8 32 10 5C 32 10 6C 32
```

正确包结构：

```text
AA 55 | CT | LSN | FSA(2) | LSA(2) | CS(2) | Si(3) × LSN
```

每一个 `Si` 不是“距离低字节、距离高字节、质量”这种旧买家驱动的解释；正确计算是：

```text
quality/intensity = ((distance_low & 0x03) << 8) | quality_low
distance_mm      = ((distance_high << 8) | distance_low) >> 2
```

上述真实包的 CS 校验结果为 `0x511D`，与报文完全一致；8 个点距离依次为：

```text
3292, 3278, 3271, 3262, 3252, 3242, 3223, 3227 mm
```

因此，板端雷达服务已按“带 CS、带 intensity 的真实协议”修正，不再按 ROS 买家驱动中的错误无 CS/错误三字节顺序解析。

### 雷达实测

正常运行时已观察到：

```text
约 392–400 原始点/圈
约 304–316 过滤后有效点/圈
约 4.2–7.9 Hz（电机转速会变化）
约 1.5–3.1 K samples/s
角度覆盖约 1°–353°，四象限均有连续回波
valid_packets 持续增长，checksum_errors = 0
```

雷达服务重启恢复时间已测得约 `324 ms`，几秒内恢复完整点云。

### 雷达源文件

```text
/home/linaro/ai/lidar/lidar_service.py
/etc/udev/rules.d/99-lidar.rules
/etc/systemd/system/rk3568-lidar.service
```

USB 设备重新插入后，udev 会重新建立 `/dev/lidar`。此前探测第二个异常 CDC 接口会导致第一接口解绑，因此**正式系统只使用 `/dev/lidar`，不要再对第二个未绑定 CDC 接口做 libusb 探测**。

若雷达页面显示 `waiting_device`，优先处理：

1. 拔插雷达 USB（不要拔摄像头）。
2. 确认圆盘电机持续旋转。
3. 检查：

```bash
ls -l /dev/lidar /dev/ttyACM*
systemctl restart rk3568-lidar.service
curl --noproxy '*' http://127.0.0.1:8091/api/radar/status
```

## 7. 融合服务：已有逻辑与注意点

融合服务不是 EKF；它是为智慧超市会话设计的离散状态机：

```text
IDLE
  → CUSTOMER_CANDIDATE
  → CUSTOMER_PRESENT
  → SESSION_END_PENDING
  → IDLE
```

逻辑：

```text
视觉：COCO person 置信度 ≥ 0.45
雷达：与“空场背景”相比，至少 2 个扇区出现更近的新目标
二者任一可形成候选；持续证据才确认顾客会话
```

重要修正：

- 不再把“雷达最近点”直接等同于有人，因为货架、桌面和底座都有静态回波。
- 使用 36 个 10° 扇区建立空场基线，只分析正前方 ±75° 区域。
- 仅“更近的新回波”可由雷达单独开会话；回波消失/抖动仅记为运动，不能单独开会话。
- 顾客离开宽限已从 1.2 秒增加至 3 秒。
- 仅在视觉确认无人时学习 12 圈空场背景，避免把人写进背景。
- 背景文件路径：`/home/linaro/ai/fusion/radar_baseline.json`。
- 融合诊断文件 `latest.json` 的写入频率已从每秒 10 次降到每秒 1 次，以降低 eMMC 写入与 CPU 占用。

### 当前待完成的融合修复

本地已完成、通过 `py_compile`、但因手机热点 SSH 传输未返回确认的版本：


该版本把融合 HTTP 页面从“和传感器轮询同一线程”改成独立线程。现有旧结构中，如果一次本地 HTTP 获取视觉/雷达卡住，`8090` 页面也会短暂无响应；新版本能让网页/API继续返回最近状态，即使某个传感器轮询短暂超时。

交接时请先确认该文件是否已经在板端临时路径：



## 11. 不应做的事情

- 不要把 XIAO ESP32-S3 的 Edge Impulse `.ino` 直接当作 RK3568 模型迁移；它是不同运行时，且目前只识别 `apple/banana/grapes`。
- 不要把通用 COCO YOLO11n 的 `bottle/cup/banana` 检测结果当成超市 SKU 识别完成。
- 不要让 Linux 用户态直接 bit-bang HX711、HC-SR04 或 WS2812 作为第一版正式方案；优先保留 ESP32-S3 实时从机。
- 不要再次尝试直接接管雷达的第二个异常 USB CDC 接口；此前会解绑 `/dev/ttyACM0` 并导致雷达离线。
- 不要在没有代表性真实商品图片的情况下进行最终 INT8 校准。
