`running : ota_0 @ 0x00020000` / `next : ota_1 @ 0x00220000`，A/B 双槽确认可用。

**2026-10-11 修复（从机 ESP32-S3）**：

方案定为 **手搓 `Update` 端点**，不复活 ElegantOTA —— 后者挂在 ESP32 的 `WebServer` 库上，而本工程自己的 `WebServer.cpp` 在 `SLAVE_MODE=1` 下整体不编译，名字还撞车。

1. 新增 `firmware/store-controller/OTA_Update.h` / `OTA_Update.cpp`：用 ESP32 核心自带的 `Update` 库 + `esp_ota_ops.h` 直接操作 OTA 分区
2. `Slave_Link.cpp` 的 `handleInbound()`：**把 body 读取挪到路由解析之后**，`/api/ota/*` 走流式写 flash（绝不进 `String` —— 1.5MB 会把堆撑爆）；顺带捕获 `X-Firmware-MD5` 头
3. `Slave_Config.h`：新增 `ENABLE_OTA`（默认 1）与 `SLAVE_OTA_RX_TIMEOUT_MS`
4. 新增客户端 `tools/ota_push_slave.py`（纯标准库，RK 侧可直接用）

```
GET  /api/ota/status           → running / boot / next_slot / slot_size / 计数
POST /api/ota/upload           body = 固件原始字节，需 Content-Length
                              可选头 X-Firmware-MD5: <32位hex>
                              可选 ?reboot=1 → 烧完自动重启
POST /api/ota/reboot           → 重启
POST /api/ota/rollback         → 切回另一个槽并重启
```

行为细节：

* 上传成功后**默认不自动重启** —— 重启会掐断正在返回的响应，客户端只看到「连接被重置」，分不清是「烧成功重启了」还是「烧失败崩了」。要自动重启就显式带 `?reboot=1`。
* `rollback` 用的是 `esp_ota_set_boot_partition(另一个槽)`，**不是** `esp_ota_mark_app_invalid_rollback_and_reboot()` —— 后者依赖 `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`，Arduino 核心默认没开，调用只会返回 `ESP_ERR_NOT_SUPPORTED`。
* **不支持 `Transfer-Encoding: chunked`**：从机是手搓 socket 服务，不解析分块。`curl -T` 在部分版本会走 chunked，必须用 `curl -X POST --data-binary @x.bin`（`tools/ota_push_slave.py` 已按整体 Content-Length 发送）。
* 分区表早已备好双槽（`otadata` + `app0`/`app1` 各 1.875MB，见 `partitions.csv`），无需改动。

**仍缺**：RK3568 侧 OTA（A/B 分区或走 SSH 部署）。

### 3.3 ❌ 低功耗 180→30 mA 已废弃

`Mode_LowPower.cpp:5` 注释：「低功耗模式 → 板子插电，已废弃」。
**判定**：**主动设计放弃，不算退化**。RK3568 典型功耗本就远高于 ESP32-S3，原低功耗叙事在新架构下不成立。
**若要保留叙事**：只能对**从机（ESP32-S3）**恢复 `Mode_LowPower`，但板子实际常供电，测不出真实收益。

### 3.4 🔁 两块自研 PCB → 主控改现成核心板

原作品：主控（ESP32-S3 核心板 V2，96.8×96.5 mm）与打印控制板均为**自研 PCB**。
现状：打印机控制板、从机（ESP32-S3）保留；**主控换成商购 ATK-DLRK3568 核心板**。

**判定**：这是"换主控"任务的必然结果，属**方案变更**而非功能缺失。

### 3.6 ❌→✅ 顾客自助结算整条链断掉（2026-10-11 修复）

**这是上一版对照漏掉的最严重一处** —— 收银员侧一直是好的，所以之前"结算闭环通过"的结论
看起来成立；但**顾客自己在终端上结账**这条路，从迁移落地起就是断的。

顾客端页面（`web/index.html`，标题「智慧超市 - 顾客端」，由 `/` 与 `/customer` 以 `open` 提供）
和手机扫码页（`web/pay.html`）**都没有登录入口**，也没有、不该有收银员会话。
而这三个端点被登记成了 `write`：

| 调用 | 页面位置 | 路由表登记 | 实测 |
|---|---|---|---|
| `GET /api/checkout?items=..&total=..&method=..` | `index.html:741 doCheckout()` | `write` | **401** |
| `GET /api/pay-confirm?orderId=..&items=..` | `index.html:754/807` | `write` | **401** |
| `GET /api/mobile-pay?order=..` | `pay.html confirmPay()` | **只登记了 POST**，且 `write` | **404** |

**为什么难发现**：`doCheckout()` 把非 `ok` 一律吞成一句
「订单通道拥挤，请重试」，`pay.html` 的 `catch(e){}` 是空的。
现场现象是「顾客点结算没反应」「扫码后点确认没反应」，**完全看不出是鉴权问题**。

**还有第二处独立故障**：`ExtRouter.check()` 的 `open` 分支直接 `return None`，
**漏设 `req.implied_confirm`** —— 与它自己 docstring 写的「能走到这里的请求要么是
顾客端公开接口…」自相矛盾。后果是 `open` 路由只要内部走到 `store_ext` 的
`privileged()`（该工程"每个特权操作 = 确认 + 幂等 + 验证 + 审计"的统一入口），
就会被「该操作需要确认：请带 confirm=true 重试」挡下。
`GET /api/mobile-pay` 降为 `open` 之后仍然 400，就是这一条。

**修复**（`rk3568/store-backend/`）：

1. `store_ext_routes.py` 路由表：`GET /api/checkout`、`GET|POST /api/pay-confirm`、
   `GET|POST /api/mobile-pay` 全部改为 `open`，并补上 `GET /api/mobile-pay`
   （`pay.html` 发的就是 GET）
2. `store_ext_routes.py` 的 `check()`：`open` 分支补上
   `req.implied_confirm = not self.require_confirm`
3. `test_store_ext.py` 新增 `[14b]` 回归测试：既锁路由表权限，也**不带任何 cookie**
   走完整条链（checkout → mobile-pay → pay-status → pay-confirm）

**为什么降为 `open` 不增加暴露面**：`store_service` 内建的 `POST /api/checkout`
与 `POST /api/order/confirm`（同样会置 PAID）**本来就没有任何鉴权**，
任何能访问 8094 的人早就能建单/确认支付。把 GET 侧对齐成 `open` 只是让页面能用。
真要收紧，得连 `store_service` 那两条一起做（顾客会话 + 限单/限速），是独立一件事 ——
**别只把这四条改回 `write`**，那只会把顾客端再次弄坏，安全性一点没变。

**板端复测（2026-10-11，全程无 cookie）**：

```
1) GET /api/checkout      200  ok=True orderId=30 total=3.5
2) GET /api/mobile-pay    200  ok=True 付款请求 #7 已创建（180 秒内有效）
3) GET /api/pay-status    200  confirmed=True status=WAITING
4) GET /api/pay-confirm   200  ok=True 支付成功
5) GET /api/pay-status    200  paid=True
```

`test_store_ext.py` 在板端 Python 3.7.3 上 **264/264 通过**（修复前 260/4 失败）。

> 副作用：上面这次实测在板端留下一条**已支付的测试订单 #30（¥3.50，现金）**，
> 会进当日营收统计。要清掉可从商家端退款。

### 3.7 ➕ 识图问答（VLM）—— **迁移时新增的能力**（2026-10-11 打通）

**这条不在原作品 37 项功能清单里**，是迁移到 RK3568 之后新加的：把板端摄像头
接到大模型视觉接口，顾客可以对着货架/桌面直接问「这是什么」「我在吃什么」。

**三段链路**（每一段都可能单独挂掉，必须分段隔离排查）：

```
RK3568 摄像头 8088 /raw.jpg
   ↓  板端 8092  vlm_client_service.py —— 纯代理，只负责取帧 + 转发
   ↓      配置 /home/linaro/ai/vlm/vlm_client_config.json（改 pc_url 后要重启服务）
电脑侧 8097  vlm_service.py —— 真正调大模型，电脑侧跑（不占板端算力）
   ↓      配置 rk3568/vlm/vlm_config.json

```

**两个根因，都不是"代码写错"，而是配置假设与现场不符：**

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 板端 `POST /api/vlm/ask` 返回 `{"ok":false,"error":"timed out"}`（21.5 s） | `vlm_service.py` 取板端帧的**超时写死 20 秒**，按"健康局域网"设的。现场实测 **ping RTT 175~1562 ms、16% 丢包，44 KB 的 `/raw.jpg` 要 36 秒** ⇒ 20 s 必然超时 | `fetch_board_frame` 默认 `timeout` 20 → **90**；`probe_board` 6 → **15** |
| 2 | 取帧修好后报 `后端 HTTP 404: Model not exist.` | 该 key 是**阿里云百炼国内账号**（`sk-ws-` 前缀），**没有 `qwen-vl-max`** | 探测 `/models`（该 key 共 175 个模型），视觉可用的是 **`qwen3-vl-plus`**（另有 `qwen-vl-ocr`）。改模型名 |

**落地的改动：**

| 文件 | 改动 |
|---|---|
| `rk3568/vlm/vlm_config.json` | `backend=openai`、`openai_model=qwen3-vl-plus`、`board_ip=10.176.240.215`、`api_key=""`（密钥只从环境变量取，**绝不入库**） |
| `rk3568/vlm/vlm_service.py` | 取帧超时 20→90、探测超时 6→15；`DEFAULT_CONFIG` 的 `openai_model` 默认值一并改成 `qwen3-vl-plus` |
| `rk3568/vlm/board/vlm_client_service.py` | `DEFAULT_CONFIG["pc_url"]` 默认值 → `http://10.176.240.242:8097`（电脑本机） |
| `rk3568/vlm/pc_start.py` | **新增**。一键起电脑侧服务：自动挑与板端同网段的本机 IP、按 `VLM_API_KEY`→`DASHSCOPE_API_KEY` 找密钥、`--check` 会列该 key 实际可用的视觉模型（防再踩 `Model not exist.`） |
| 板端 `/home/linaro/ai/vlm/vlm_client_config.json` | `pc_url` → `http://10.176.240.242:8097`（**两边都要改，只改一边不通**） |

**端到端实测（2026-10-11）**：`python rk3568/vlm/pc_start.py --check` → 模型可用；
取帧 43,122 B / 1.3 s；`qwen3-vl-plus` 推理 2.3 s，回答
「图中是一个人坐在桌前，手托着脸，桌上放着手机、笔和纸张，背景有强光从窗户照入。」

## 5. 结论

**招牌能力无退化。** 原作品最硬的四张牌 —— 多模态融合（0.78/0.22）、AI 两阶段授权、自研打印协议、语音+距离双条件唤醒 —— **全部在迁移后保持可用，且实测通过**。

**但"静默功能丢失"确实发生过一次**：顾客自助结算整条链（§3.6）—— 页面把 401/404
吞成一句「订单通道拥挤」，从界面上完全看不出来。这条是靠**逐条核对页面实际发出的
请求与路由表权限**才挖出来的，不是靠点页面。**结论里"没有静默丢失"这句话在 2026-10-11
之前是不成立的**，这里如实修正。

需要收尾的项，按"是否缺能力"分两类：

| 类别 | 项 | 状态 |
|---|---|---|
| **不缺能力，只缺配置/改动** | `ai.mimistore.icu` 域名 | App 的 AI 导购在等它；网页版不受影响 |
| | Android App 的旧 IP | ✅ 已改并重出 APK v1.5.4 |
| | 飞书入站 webhook | 配 App 凭据即起 |
| | 顾客自助结算 401/404 | ✅ 已修并在板端复测（§3.6） |
| **真缺能力** | OTA | 🔁 MimiClaw（`ota` 命令）+ 从机（`POST /api/ota/upload`）已补；只剩 RK3568 |
| | 低功耗 180→30 mA | 架构变更后的主动放弃（RK 板常供电） |
| **迁移新增** | 识图问答（VLM） | ✅ 已打通并实测（§3.7）。注意电脑侧 8097 非常驻，重开机要 `pc_start.py` 拉起 |

**遗留的开放性风险**（不是迁移造成的，是原工程就有的，但迁移后值得知道）：

* **8094 的收银/支付接口对局域网完全开放** —— `POST /api/checkout`、`POST /api/order/confirm`
  无任何鉴权，同网段任何人都能建单/把订单标成已支付。本次把 GET 侧对齐成 `open`
  没有改变这一点，只是让页面能用。要收紧需引入顾客会话 + 限单/限速，是独立一件事。
* **顾客端页面上有「遇到问题？强制放行」按钮**（`index.html manualConfirm()`），
  顾客一键就能把订单置 PAID。这是原工程的设计，保留至今。
